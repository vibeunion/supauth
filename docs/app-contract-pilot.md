# App 契约试点

## 当前实现（2026-09-14）

管理台已从历史的 `@supacloud/app/contracts` 入口切换到独立的
`@supacloud/contracts@0.3.1` / `@supacloud/contracts/client` 入口。
下文保留的 2026-09-09 验收数字和 `@supacloud/app@0.11.0` 依赖证据仅作为历史基线；
当前实现不再将 `@supacloud/app` 作为管理台运行时依赖。

## 范围

首轮试点只接入管理台的自定义登录页资源删除流程，当前使用固定版本
`@supacloud/contracts@0.3.1` 的 `@supacloud/contracts/client` 入口。
不迁移路由、依赖注入、认证守卫、GoTrue 权威、数据库或部署方式。

目标是把一次写入及结果确认的公共执行规则交给上游契约客户端，
让页面只管理交互状态、持久锁和提示。它不是“更换框架即可消除 bug”的证明。
Webhooks、批量设置保存、服务器命令治理不在首轮范围内。
2026-09-09 的第二轮仅增加 Webhook 列表启停，详见下方“第二轮复用”；
首轮验收数字保留为历史记录，不代替第二轮验证。

## 必须保留的行为

- 删除前持久化操作锁；锁未确认或存储不可用时，禁止继续写入。
- 每次操作最多一次 DELETE 和一次自动 GET；不自动重放 DELETE。
- DELETE 成功也必须读取权威状态，不能仅靠写入回执宣布完成。
- `send` 与 `lookup` 共用同一次状态读取，包括失败的读取。
- 只有写请求本身的明确拒绝可以按拒绝处理；读取失败不代表写入失败。
- 超时、未知异常、无效数据、不同资源回执不能自动解锁。
- 继续使用 shared 的状态 Schema 和现有资源生命周期匹配规则。
- 页面刷新恢复未决锁；手动确认只读取状态，保留原有人工解除流程。

确认仍采用现有的生命周期规则：同一资源进入清理状态，或完整进入无资源的
`disabled` 状态。DELETE 接口没有新增期望资源版本或命令 ID，因此这不是
后端持久命令回执，也不提供跨客户端的严格只执行一次、原子 localStorage 锁，
或服务端按前端目标版本进行原子比较删除的保证。确认最终状态和证明某次
请求恰好执行一次是两回事；这些既有接口边界不能由更换客户端 helper 消除。

## 收益与成本

此试点把页面内分散的自动写入确认分支替换为一个可独立测试的领域适配器，
但保留业务自己的生命周期规则、持久锁和错误展示。
新增适配器、故障测试以及包依赖都有维护成本，不能只统计删除的页面行数，
也不能把测试用例数量当作故障率下降的证据。

相对本次修改前的类型安全验收快照，页面由 342 行变为 332 行，
新增领域适配器 109 行，生产代码合计净增 99 行（不计测试、文档和锁文件）。
实际删除的是 `reconcileLockedMutation`、`recordMutationFailure` 两段自动编排，
不是生命周期校验或持久锁。

本次同时收紧一项有源码证据的错误分类：服务端可能在停用资源或删除对象后
返回 `409 custom_ui_changed_retry`；旧页面会通过
`!mutationOutcomeUnknown(error)` 把它当作明确失败并解除锁。
新适配器只把 DELETE 写阶段的 `AdminApiError` 401/403 作为明确拒绝，
其余错误必须读取权威状态确认或保留未知结果。该修正不依赖“类型检查通过”
来推定业务正确，而由副作用后 409、读取 403 和目标不匹配的回归场景验证。

是否扩大采用，要根据后续真实缺陷和修改成本判断：
同类流程能否复用、是否真正删除重复实现、错误路径是否保持一致、
以及新增依赖和兼容适配的成本是否值得。试点本身不授权整体迁移。

## 第二轮复用

2026-09-09 将一写一读确认协议提取到 `authoritative-command.ts`，
由原 Custom UI 删除和新 Webhook 列表启停共同使用；依赖版本不变。
不迁移其他 Webhook 操作、路由、服务端或数据库。

- 公共执行器负责外部数据校验、一次写入、缓存一次自动读取、阶段化错误记录。
  输入和读取解码允许转换数据形状，各执行一次；SDK 内部仅接受本次已校验
  对象的身份凭据，不能用转换后的数组冒充原始分页响应。
- 领域适配器保留生命周期、目标匹配和拒绝分类；页面保留持久锁以及操作、
  列表请求的双重过期保护。
- Webhook 更新后还会写审计，因此 PUT 的 401/403/409 均不能直接解锁：
  仍须完整权威读回匹配捕获的 ID 和目标启停值。无默认授权错误分类。
- 权威列表必须满足 shared Schema、完整第一页、分页容量一致和全列表 ID
  唯一；空白 ID、重复冲突、缺项、错误目标或读取失败都不能授权自动重试。
- 只有输入校验失败才能证明本次尚未发送请求；结果未知不自动重放。
  已确认但清锁失败仍保留可见锁。确认仍是最终状态收敛，不是持久命令回执。

相对本轮开始的快照，Custom UI 适配器从 109 行缩至 54 行，
新增公共执行器 102 行、Webhook 适配器 48 行，Webhook 列表从 1235 行
变为 1251 行；底层请求选项增加 16 行，严格令牌获取增加 6 行，
Custom UI 页面从 332 行变为 341 行，生产代码合计净增 142 行
（不含测试和文档）。
删除的是 Custom UI 的独立缓存读取/执行编排和 Webhook 的内嵌错误确认分支；
业务规则与页面锁没有被虚假计作“消除的重复代码”。

这证明了两个流程可以共用受测协议，但**尚不能证明整体采用
`@supacloud/app` 会降低维护成本或线上故障率**。本轮发现的转换解码、
审计后授权错误与分页证据问题都需要领域校验和回归测试，框架本身不会
自动补齐。当前继续限定使用 `/contracts`，不整体迁移，也不引入
`pg_graphql`：本轮没有数据库查询表达或读取组合方面的需求，
改变查询入口不能解决写入确认、重试与持久锁问题。

### SSO 隐藏重放

最终源码审查发现已安装 SSO 客户端会在 401 后刷新令牌并重发原请求，
不限 HTTP 方法。由于 Webhook 更新后的审计可能返回 401，
“执行器调用一次 write”并不足以保证 HTTP PUT 不被再次发送。
因此第二轮必要地扩展到 `admin-api.ts` 的窄请求策略：

- 两个试点页面仅在写请求上设置 `authenticationRetry: "never"`。
- 发送前通过现有令牌提供者取得当前令牌，随后使用原生 fetch 单发；
  缺少令牌时明确拒绝且不发送请求，不把安全选项当作 HTTP 参数外泄。
- 已配置 SSO 身份源时，严格令牌获取保留其空会话结果，不回退浏览器中
  残留的旧版令牌。无身份提供者时仍支持原有令牌登录；默认取令牌行为不变。
- 401 后不进入认证重放分支；读取和其他请求保持原认证刷新行为，
  请求超时、中止、输入及响应 Schema 校验不变。
- 这一策略只保证本应用所控请求链路不自动重放试点写入，
  不代表全站关闭重试，也不证明服务端或代理层的 exactly-once。

原生 fetch 单发并不是绕过认证：Authorization 使用同一当前令牌，
请求仍携带原有凭据与中止信号，服务端授权仍然生效。
发送前令牌过期时允许正常刷新；禁止的是写入后的刷新重放。
一次缓存的逻辑读取仍可能经过 SSO 刷新产生两次只读 HTTP GET，
因此不能把逻辑读取次数当作全认证模式下的网络请求次数。
验收需同时覆盖实际 SSO 客户端的刷新对照与两个页面的真实选项接线；
仅使用固定 token 的浏览器场景不能证明 SSO 路径满足此规则。

### 导航与持久锁

实际浏览器复现了两个页面的同类缺陷：写入后的状态读取尚未完成时，
离开页面再返回，新页面已恢复持久锁；旧页面的读取随后完成，却清掉了
该锁。旧组件不更新屏幕并不代表其存储副作用已经失效。

两个试点命令现在都记录页面卸载状态，拒绝卸载后的完成处理。
Webhook 原有操作和列表 generation 检查同时保留；
Custom UI 清锁入口也拒绝已卸载页面，覆盖延迟的手动状态确认。
页面本地检查不能被描述为跨标签页原子锁，状态未知仍需当前页面只读确认。
浏览器验收需同时检查当前界面和 localStorage，而不是只检查页面无异常。
